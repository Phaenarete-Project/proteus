## 2. 13 条断言逐条复核

### 2.1 B1：证据 kind/status/evidence_id/删证据/悬空 refs

**已修复。** 复现方式：create → verify（正确答案）→ 在 ledger 中篡改 → finalize → audit verify。实测：

| 篡改 | finalize | audit verify |
|---|---|---|
| 把 numeric evidence 的 `kind` 改成 `symbolic` | `ok:true, state:LowConfidence, reason_codes:[EVIDENCE_CONFLICT]` | `ok:false`；issues 含 `EVIDENCE_KIND/EVIDENCE_DIGEST/EVIDENCE_ID/EVIDENCE_MISMATCH/GRADE_MISMATCH/STATE_MISMATCH` |
| `status` 改成 `fail` | LowConfidence + EVIDENCE_CONFLICT | `ok:false`（EVIDENCE_DIGEST/EVIDENCE_ID/EVIDENCE_MISMATCH/STATE_MISMATCH） |
| `evidence_id` 改成 `ev_000000000000` | LowConfidence + EVIDENCE_CONFLICT | `ok:false`（EVIDENCE_MISMATCH/EVIDENCE_EXTRA/STATE_MISMATCH） |
| 删一条证据 | LowConfidence + EVIDENCE_CONFLICT | `ok:false`（EVIDENCE_MISMATCH/EVIDENCE_EXTRA/STATE_MISMATCH） |
| 悬空 `evidence_refs` | LowConfidence + EVIDENCE_CONFLICT | `ok:false`（`DANGLING_EVIDENCE_REF` + STATE_MISMATCH） |

对应实现：`lib/evidence.js:366-448`（kind 参与哈希、`validateEvidenceRecord`）；`lib/tools.js:282-321`（finalize 重跑 + 悬空 refs）；`lib/audit.js:256`（audit 侧逐条校验）。

### 2.2 B2：伪造 state/grade / 无效 contract

**按 Lead 断言已修复，但不完全。** 复现：

B2 forged state/grade verify ok=false issues= GRADE_MISMATCH,STATE_MISMATCH

## 3. 新发现 / 残留问题

### 3.1 R1（Blocker，残留）：审计包的 `environment.evidence_min_kinds` 可被伪造，从而把 numeric-only 证据认证为 `Verified`

- **复现**：从真实 finalize 包出发，只改两个字段并重算 `bundle_id`：
  1. `environment.evidence_min_kinds = 1`；
  2. `state = {state:"Verified", reason_codes:[], decided_at:...}`。
  
  实测：
  ```
  real state LowConfidence kinds [ 'numeric' ] minKinds 2
  direct verifyBundle forged: [] true
  tool verify: true
  tool replay: true []
  ```
  即 `proteus_audit verify` 与 `replay` 都返回 `ok:true`，尽管该包只有 1 类 numeric 证据，而实际部署配置是 `evidenceMinKinds=2`。
- **原因**：`lib/audit.js:474` 使用 `bundle.environment.evidence_min_kinds`（攻击者可控）作为重算终态的 `minKinds`；`verifyBundle` 没有拿到 `ctx.cfg.evidenceMinKinds`。同类地，`environment.evidence_min_kinds=0` 可让无证据包也判 Verified（只要 grade/state 按该配置自洽）。
- **为什么是 blocker**：这正好绕过本轮要修的 B2；也违反 `审计包.md` 的“v0.1 下任何 Verified 都应按异常处理”。攻击者不需要伪造证据，只需把“门槛”改低，审计工具就会自己盖章。
- **修复建议**：`handleAudit verify/replay` 把 `ctx.cfg.evidenceMinKinds`（或至少固定 2）传给 `verifyBundle`/`verifyBundleSemantics`，要求 `bundle.environment.evidence_min_kinds === 期望值`；或者直接不信任环境字段、始终用运行时配置。补负例测试：把 env 改成 1/0 后 verify 必须 `ok:false`。

### 3.2 R2（Major）：`cwd`/`bundle_path` 的路径收敛未解析 symlink，可写到工作区外

- **复现**（实测）：
  ```
  工作区内新建 link-out -> /tmp/<outside>
  proteus_contract create {cwd:'link-out'} => ok:true
  读取 /tmp/<outside>/proteus/ledger/<hex>.json => {"schema":"proteus.ledger/v1",...
  ```
  文件确实写到了会话工作区之外。
- **原因**：`lib/tools.js:162-183` 仅做 lexical `isWithin(relative(...))`；没有 `realpath`。同样问题可用于 `bundle_path`（audit 目录内 symlink 指向外部文件）。
- **修复建议**：对 `base` 与候选路径都 `realpath`（不存在时对最近存在祖先 realpath 再拼接），再做前缀判断；对 `rootDir`/`auditDir` 也做一次 realpath；或禁止 `cwd` 参数为 symlink。补 symlink 负例测试。

### 3.3 R3（Major）：矩阵失败时 finalize 已写解答与审计包，留下“可 verify 的失败快照”

- **复现**：矩阵路径变成目录 → `finalize` 返回 `MATRIX_WRITE_FAILED`、ledger.state 仍 `verified`；但 `<root>/solutions/<hex>.md` 和 `<root>/audit/<hex>.json` 已存在，且 `proteus_audit verify` 返回 `ok:true`。
- **为什么是问题**：设计/规范要求 finalize 三步（解答、审计、矩阵）缺一即失败、审计包应代表一次成功 finalize；失败后留下可 verify 的包会误导调用方/审计者（且 `audit write` 会因旧包可 verify 而直接返回它）。这是 M3 修复的原子性残留。
- **修复建议**：把 `writeBundle`/`writeTextAtomic(solution)` 移到矩阵成功之后；或先写临时文件、矩阵成功后再 rename；失败路径清理已写文件；补“矩阵失败后 audit 不存在/不可 verify”测试。

### 3.4 R4（Major，新）：未调用 verify 的 finalize 返回 ok，但产出的审计包无法通过 verify

- **复现**：
  ```
  no-verify finalize: true LowConfidence [ 'EVIDENCE_INSUFFICIENT', 'EVIDENCE_CONFLICT' ] conflict true
  audit verify false EVIDENCE_MISMATCH,EVIDENCE_EXTRA×4,GRADE_MISMATCH,STATE_MISMATCH
  final.verification null
  ```
  原因：finalize 在没有 `ledger.verification` 时仍按全量 plan 重跑并发现 `EVIDENCE_EXTRA`，但直接把 `verification:null + evidence:[]` 写入包；audit 语义层再按全量 plan 重跑，必然不一致。
- **为什么是问题**：finalize 的契约是“定稿必留可审计包”；现在一条合法工具路径会产出一个自相矛盾的包。对“不会做/Unknown 但 finalize”的路径尤其相关。
- **修复建议**：二选一：a) finalize 要求 `ledger.verification` 存在，否则返回 `VERIFY_REQUIRED`；b) 无 verify 时把 `verification.plan=[]`、`evidence=[]`，并让 audit 在同一空 plan 下重跑（或标记 `auditable:false`）。补“无 verify finalize”测试。

### 3.5 R5（Minor）：`answer` 摘要按原始 JSON 计算，`unit:null` 与缺省 `unit` 被视为不同

- **现象**：verify 用 `{answer:{value:'2',unit:null}}`、finalize 用 `{answer:{value:'2'}}` 时，finalize 报 `EVIDENCE_CONFLICT`、audit 报 `EVIDENCE_DIGEST`；内容语义相同。
- **原因**：`evidenceHashes` 的 `answer` 直接 `digest(solution.answer)`（`lib/evidence.js:366-377`），没有把缺省 `unit:null` 归一。
- **建议**：在 `normalizeContract`/solution 入口统一归一 `answer`（`{value, unit:null}`），或在文档/测试中明确“verify 与 finalize 必须传完全相同的 answer 对象”。非阻塞。

### 3.6 R6（Minor，未在本次清单）：T18 仍与技能说明不一致

- 技能：`domain=probability` **且** `problem_type ∈ {computation,classification}` 且无 `cases:N`（`陷阱库.md:209`）。
- 代码：`domain=probability` **或**题面含“排列/组合/计数/种数/多少种”（`lib/traps.js:397-405`），无 problem_type 门槛；选择题概率题会被误扣。
- 修复建议：给 T18 加 `problem_type` 门槛，或更新技能/规范；加一个 probability + multiple_choice 的反例测试。

## 6. 交付判断

**如果“可验证、可审计、证据不可伪造”是交付门槛：现在还不能给通过。** 必须项：
