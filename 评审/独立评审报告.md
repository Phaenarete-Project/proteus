## 2. 发现清单（按 severity 排序）

### 2.1 Blocker（2）

#### B1. 证据 `kind` 可被篡改，v0.1 能凭空拿到 `Verified`，且 `audit verify` 与 `replay` 都放行

- **证据**
  - `lib/rubric.js:17-23`（`passKindsOf`）与 `lib/tools.js:217-262` 只按 evidence 的 `kind` 计独立种类；`lib/evidence.js:365-385` 的 `evidence_id` = `sha256(input_digest|output_digest|check|claim)`，**`kind` 不参与哈希**。
  - `lib/tools.js:557-574` finalize 只 `gradeSolution()` 重算分数，**没有重新核对账本 evidence 的 digest/kind/claim**（设计 §6.3 第 3 道闸“发现 status 被改过直接判 EVIDENCE_CONFLICT”未实现）。
  - `lib/audit.js:195-205` 只重算 `output_digest` 与 `evidence_id`；`lib/tools.js:729` replay 只比较 `status/detail/evidence_id`，**不比较 `kind`**。`lib/audit.js:172-176` 只校验 kind 在枚举内。
  - 实测（临时目录，完整链路）：
    ```
    before forge: numeric ev_d72b99b53c73
    finalize with forged symbolic kind => Verified [] kinds [ 'numeric', 'symbolic' ]
    audit verify: true none
    audit replay: true none
    ```
    操作仅为把账本里一条 `expression_sample` evidence 的 `kind: "numeric"` 改成 `"symbolic"`，其余字段（含 evidence_id）不动。因为所有预设都带 `tool-fs`，解题者角色可以合法地直接编辑 `<root>/ledger/*.json`。
- **为什么是问题**：这直接击穿“证据只能由工具生成、模型不能伪造”的核心不变量。更严重的是，它让 v0.1 本来刻意不可达的 `Verified` 变成一条字段编辑即可达，且**现有两个审计工具都检测不到**；设计 §6.3 的“定稿第三道闸”与 SKILL §5.2 “悬空/伪造引用记 EVIDENCE_CONFLICT”均成空文。
- **修复建议**
  1. `evidence_id` 哈希纳入 `kind` 与 `check` 的映射（`CHECK_META`），并在 `verifyBundle`/replay 中强制 `kind === 该 check 的固定 kind`；`finalize` 对账本 evidence 逐条重算 `input_digest`/`output_digest`/`evidence_id`，任一不符直接 `EVIDENCE_CONFLICT` 并降级。
  2. 账本增加不可被同角色直接改写的保护（至少：finalize 只认“本次 verify 返回并登记在 ledger.timeline 的事件所对应的 evidence”；或把 evidence 摘要写进一个由 Host 侧 HMAC/独立状态文件保护的位置）。
  3. 补负例测试：改 `kind`、改 `status`、改 `evidence_id`、删 evidence、悬空 `evidence_refs` 五种情况都必须让 finalize/verify 失败或降级。

#### B2. 审计包的结论字段（`state`/`grade`）不被校验，伪造后 `audit verify` 与 `audit replay` 均返回 ok

- **证据**
  - `lib/audit.js:294-356` 的 `verifyBundle` 只做：bundle_id、contract_id/matrix_cell 摘要、evidence 形状/摘要、grade 的“形状与范围”、state 枚举、timeline 链、environment 警告。**不重算 grade、不重跑 state 判定、不调用 `validateContract(contract)`、不检查 `budget` 与 state 是否矛盾。**
  - `lib/tools.js:702-753` 的 replay 只重跑 `runChecks` 并比对 evidence；**不比较 grade/state**。
  - 实测（只改结论，不动 contract/solution/evidence/timeline）：
    ```
    B real: LowConfidence pred 0 / 12
    B forged verify ok= true issues= none
    B forged replay ok= true diffs= 0
    ```
    伪造内容：`state.state="Verified"`、`reason_codes=[]`、`grade.predicted_points=max_points`，再重算 `bundle_id`。
  - 同一根因的第二个实测：把契约 `domain` 改成 `astrology`（`validateContract` 判 invalid），重算 contract_id/matrix_cell/bundle_id 后：
    ```
    C invalid-contract self-consistent bundle verify ok= true issues= none | validateContract says invalid
    ```
  - 文档要求 vs 实现：
    - `spec/INTERFACES.md:278`：“verifyBundle：重算 bundle_id、逐条重算 timeline 链、校验 evidence digest 与 grade 一致性。”
    - `skills/proteus/审计包.md:62-67`：verify 做四件事，第 3 条“重算 input/output digest”，第 4 条“用 rubric 重算 grade 并比对 predicted_points/step_scores/deductions”。
    - `skills/proteus/审计包.md:93-110` 与 `presets/persona-proteus-auditor.md:43-70` 把“重算 grade、contract 通过 validateContract、budget 与 state 不矛盾、finalize.done 事件”都列为审计必过项——这些工具全都没做。
- **为什么是问题**：审计包被设计为“信任根”和“可重放”的最终凭证；现在一个只改两行 JSON 的伪造包能被 `verify` 判 ok、被 `replay` 判 ok，审计结论本身不可信。这直接违反随笔 §四.4“任何人拿到这个包都能复现答案和评分”和设计 §10「三层可验证性」。
- **修复建议**
  1. `verifyBundle` 增加语义层：`validateContract(bundle.contract)` 必须是 `ready`（或与 state 一致的 ambiguous/out_of_syllabus）；用 `bundle.contract + bundle.solution + bundle.evidence` 重算 `grade` 并逐字段比对；按 §2.9 重算 state 并与 `bundle.state` 比对；校验 `budget` 与 state 的降级关系；校验 `solution.steps[].id` 与 rubric 对齐、`evidence_refs` 全部存在。
  2. replay 在证据比对之外，同样重算 grade/state，并把差异写进 `diffs`（区分 `GRADE_MISMATCH`/`STATE_MISMATCH`）。
  3. 补负例测试：伪造 state、伪造 grade、无效 contract、`exhausted` 却 Verified、悬空 refs、step id 与 rubric 不一致，均必须 `ok:false`。

### 2.2 Major（15）

#### M1. 证据没有“撤销/最新版本”语义：改对答案后旧 `fail` 永久污染状态，正常“fail → 修 → verify”流程永远带 `EVIDENCE_CONFLICT`

- **证据**：`lib/tools.js:517-520` 只按 `evidence_id` 去重后追加，从不淘汰旧答案的证据；`lib/tools.js:565` 与 `decideFinalState` 的 `summary` 永远统计整本账本。实测：先 verify 错误答案（4 条中 2 fail），再 verify 正确答案（新增 4 条 pass），finalize 返回：
  ```
  finalize after corrected answer: LowConfidence [ 'EVIDENCE_CONFLICT', 'EVIDENCE_INSUFFICIENT' ]
  summary { pass: 6, fail: 2, total: 8 }
  ```
  最新证据全 pass，但状态原因仍含旧的 fail；等 v0.2 接入 symbolic 后，这条旧 fail 会让 `Verified` 永久不可达。同时 `handleVerify` 对 `ledger.state === 'finalized'` 仍可追加证据（`lib/tools.js:520` 只在 created 时改状态），审计“冻结快照”名不副实。
- **为什么是问题**：设计 §2.4“失败要诚实，且失败要可分类”要求修正后可重新判定；当前语义把“曾经错一次”永久写进最终结论，既不诚实也不可用。审计包还会同时包含新旧两套证据，replay 靠 `Map` 后写覆盖来“碰巧”通过。
- **修复建议**：引入 `supersedes`/`attempt_id` 或“每 check 取最新 attempt”；`decideFinalState`/`grade` 只看当前 attempt 的证据；保留旧证据供审计但标记 `superseded`；`finalize` 后拒绝 `verify/grade/finalize`（或要求新 contract_id）；`replay` 按 attempt 比对。

#### M2. `finalize` 可重复调用：覆盖 `solutions/` 与 `audit/` 快照、矩阵 attempts 可刷高、`audit write` 产生不同 bundle_id

- **证据**：`lib/tools.js:547-640` 的 `handleFinalize` 没有检查 `ledger.state === 'finalized'`，同一 contract_id 再次 finalize 会重写 `solutionPath`、`writeBundle`（`lib/store.js:57-59` 路径只由 contract_id 决定）、再 `upsertOutcome` 一次；`lib/tools.js:583-620` 先写 bundle、再在 `lib/tools.js:638-640` 写 `finalize.completed`，所以**已经写出的包里没有完成事件**。实测：
  ```
  matrix attempts before/after second finalize: 2 -> 3
  real bundle timeline: contract.created -> evidence.appended -> ... -> finalize.decided (无 finalize.completed)
  ```
  `proteus_audit write` 重建时用新 `at` 和新 timeline，bundle_id 与 finalize 那份不同（我实测两次 id 不同），与 `spec/INTERFACES.md:407`“覆盖等价内容”和 `审计包.md:132`“只读快照，一旦生成即冻结”冲突。
- **为什么是问题**：审计包按 contract 命名，旧包会被静默覆盖，无法证明“当时交的是哪一份”；矩阵是审计对象，重复 finalize 可直接抬高 attempts/verified/correctness，正是设计 §5.2 想防的“模型通过多报 attempts 伪造覆盖率”。
- **修复建议**：finalize 幂等化（同 contract+solution+evidence 计算内容哈希，重复 finalize 直接返回既有 final；不同 solution 则拒绝并提示新契约）；audit 文件名加入 solution/bundle 摘要或 attempt 号；矩阵只在“首次 finalize 该 contract+solution 内容”时 +1；把 `finalize.completed` 写进 bundle 后再落盘。

#### M3. 矩阵写失败只记 warning，finalize 仍返回 ok，违反“解答/审计/矩阵三者缺一即失败”的硬不变量

- **证据**：`lib/tools.js:622-636` 用 `try/catch` 包住 `loadMatrix/upsertOutcome/saveMatrix`，失败仅 `warnings.push('MATRIX_WRITE_FAILED')`；设计 §3.4 第 4 条与 `spec/INTERFACES.md:399` 明确“写解答 → 写 audit bundle → 更新 matrix → ledger.state=finalized …三者缺一即失败”。实测把 `<root>/matrix.json` 变成目录后：
  ```
  finalize with broken matrix: ok= true warnings= [ 'MATRIX_WRITE_FAILED' ] state= LowConfidence
  ```
- **为什么是问题**：矩阵是五维统计与评测结论的来源；静默丢一次更新会让 coverage/correctness 与审计包不一致，且模型/nobody 能发现。
- **修复建议**：矩阵失败即 `throw`，ledger 不置 finalized，返回 `MATRIX_WRITE_FAILED`；若要容错，至少把矩阵写入纳入同一个“final 成功”条件，并在 audit bundle 记录 `matrix_write: failed` 让审计可见。

#### M4. `replay` 与 `verify` 的执行参数不一致：合法的 `checks` 子集包会被判“不可重放”，`seed` 覆盖也能让 replay 必然不一致

- **证据**：`lib/tools.js:702` replay 用 `buildPlan(contract)`（按 `contract.verification.checks` 的全量）重跑；而 `proteus_verify run` 允许 `checks` 子集（`spec/INTERFACES.md:378`、`test` 工具参数 `enum` 均支持）。实测只跑 `checks: ['answer_format']` 后 finalize，再 replay：
  ```
  A replay ok= false diffs= numeric_residual:EXTRA_IN_REPLAY,expression_sample:EXTRA_IN_REPLAY,domain_probe:EXTRA_IN_REPLAY
  ```
  另外 `handleVerify` 的 `seed` 取 `args.seed`（`lib/tools.js:515`），而 audit bundle 的 `environment.seed` 来自 `contract.verification.seed`（`lib/audit.js:80`）：verify 时用其他 seed 产生的证据，replay 用契约 seed 必然对不上；且模型可反复换 seed 直到 `expression_sample` 在 8 个采样点上碰巧全过（v0.1 可伪造面）。
- **为什么是问题**：README/规范把“可选 checks”当正常用法，却产生不可重放的审计包；这是“可重放率”指标的假阴性。seed 覆盖则破坏设计 §2.2“同一 input 同一结论”的确定性承诺，并给模型挑采样点留了空间。
- **修复建议**：在 ledger 记录本次 verify 的 `plan`（check ids）与 `seed`，replay 严格按该 plan+seed 重跑（或把“实际执行计划”写进 audit bundle）；seed 只允许契约 seed（忽略/拒绝 args.seed，或写入 environment 并在 replay 使用）。

#### M5. 步骤级证据并不存在：`verify` 永远产 `claim:"answer"`，评分却允许任意 step 回引同一条 answer 证据

- **证据**：`lib/evidence.js:405` 固定 `claim: 'answer'`；`buildPlan/runChecks` 没有任何 step 级 check。`lib/rubric.js:28-29` 用 `item.claim === step.id || referenced.has(item.evidence_id)` 取步骤证据——所以模型只要把同一条 numeric evidence 的 id 填到所有步骤的 `evidence_refs`，所有要求 numeric 的步骤都判 full。实测“全链路”中 S2/S3 回引同一批 answer 证据即可满分。`skills/proteus/输出协议.md:46-66` 与设计 §2.3 的 `claim: "S1"` 示例、设计 §10.1“每步标 evidence 种类”均无法由工具产生。
- **为什么是问题**：设计 §2.3 承诺“步骤证据引用来自工具”“每步标证据种类”，实际是“答案级证据被复制到所有步骤”。这让 `earned` 的“步骤分”很大程度由模型自报的引用关系决定，削弱“步骤分可机械计算”的核心卖点；也是 B1 之外的第二条步骤分伪造面。
- **修复建议**：至少为每个 step 生成 `claim=step.id` 的检查（哪怕只是 structural/格式归属检查），或显式规定“步骤分证据只认 answer 级且必须在评分说明中写明这是答案级回引”；把 `claim` 纳入 evidence/审计校验；更新 输出协议 与设计示例，去掉不存在的 step 级 claim。

#### M6. 输出协议（六区块 A–F、每步证据种类、F 区未验证项）与实际 `renderSolutionMarkdown` 不一致，主控收尾清单无法完成

- **证据**：`skills/proteus/输出协议.md:13-24` 规定 A–F 六区块，`:46-56` 规定 `### S1（2/2）〔structural〕`、`证据:` 行、无证据标 `heuristic`，`:93-108` 规定 E 状态行 + F 未验证项；实际 `lib/tools.js:264-374` 生成的是「契约摘要/题目/答案/步骤/评分预测/验证状态/陷阱检查/证据/审计」9 个区块，没有 A–F、没有每步 `〔kind〕`、没有 `证据:` 行、没有 heuristic 标记、没有 F 区。主控 persona 却要求“六区块齐全”“F 区没留空”（`presets/persona-proteus.md:110,115`）。设计 §10.1（`:438-478`）已经改成与 renderer 一致，于是**同一插件内存在两套互相冲突的输出模板**。
- **为什么是问题**：随笔 §四.4 与设计 §1 #8 把“面向评分者的解释层”当作四层之一；评分者按 输出协议 检查会缺 F 区/每步证据，主控按收尾清单会永远打不满勾。这是“文档承诺了、代码没兜住”的典型。
- **修复建议**：二选一并同步：a) 让 renderer 输出 A–F 并加每步证据种类/`heuristic` 标记；b) 把 输出协议 改成实际 9 区块并去掉 persona 的“六区块/F 区”要求。推荐 b) 的低成本版本 + 在步骤标题里补 `〔kinds〕`（数据已在 grade step_scores 的 `kinds` 里但未渲染）。

#### M7. `proteus_contract show` 返回的是 ledger 生命周期状态（`created`/`verified`/`finalized`），不是契约状态（`ready`/`ambiguous`/…），解题者按 persona 无法确认 `state=ready`

- **证据**：`lib/tools.js:381-391` `show` 返回 `state: ledger.state`。实测 create 后：
  ```
  show.state = created | contract ready? ready
  ```
  `presets/persona-proteus-solver.md:18` 却要求“`proteus_contract show` 拿到契约并确认 `state = ready`”。解题者会看到 `created` 而停或误判。
- **为什么是问题**：这是角色间交接的核心字段（设计 §12.4“契约官→解题者：state=ready”）。字段名相同、语义不同，会让模型/审计者误判；也解释了为什么 `show` 的测试只断言 `'created'`（`test/tools.test.js:86`），测试固化了错误语义。

#### M10. `coverage`/`confidence` 把“部分证据、0 分”的步骤算成 verified，估值被抬高

- **证据**：`lib/rubric.js:79` 失败分支返回 `verified: satisfied.length > 0`；`:141-142` 用该 flag 计算 `stepsVerified/coverage`；`:145-149` 用 coverage 算 confidence。一个 `required:true, evidence:['structural','numeric'], partial:'all_or_nothing'` 的步骤，只满足 structural（文本非空）时 `earned` 为 0，却 `verified=true`，于是 coverage 和 confidence 都按“已验步骤”计。当前测试（`test/rubric.test.js:54,58`）只覆盖全满足场景，未覆盖“部分满足但 0 分”。
- **为什么是问题**：设计 §7.2 明确 `coverage = verified_steps / total_steps`、confidence 是“证据覆盖度”；把 0 分步骤记入 coverage 会让 GradePrediction 的置信度和覆盖率系统性虚高，而这两个字段会进入审计包并被评分者读取。
- **修复建议**：`verified` 仅当 `requiredKinds` 全部满足（即 `full`）时为 true；或把 coverage 改为“full evidence 的步骤数 / 总步骤数”；补单测：`['structural','numeric']` 只有 structural 时必须 `coverage.steps_verified=0`、confidence 相应下降。

## 5. 测试缺口清单（最小必测用例）
